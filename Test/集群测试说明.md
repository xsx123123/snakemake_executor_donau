# 多瑙集群测试入口

先更新安装插件，并在登录节点加载 Donau 环境，使 `dsub`、`djob`、`dkill` 都在 PATH 中。脚本使用当前 Python 的 Snakemake；先执行 `python3 -m snakemake --version` 确认环境。

```sh
python3 -m pip install -e .
cargo build --release --locked --manifest-path rust/Cargo.toml
python3 Test/run_cluster_tests.py --help
```

如果使用已携带 sidecar 的平台 wheel，可以省去 Cargo 构建；否则按以下命令用 `--sidecar-path "$PWD/rust/target/release/donau-sidecar"` 指定构建产物。

## 1. 先 dry-run，再小规模验证

以下以 `fat_x86` 为例，替换成你的真实测试队列。每次新测试使用独立输出目录，不影响仓库或其他工作流的 results。新测试需要空目录；脚本不删除旧数据或 journal。

```sh
python3 Test/run_cluster_tests.py --queue fat_x86 --samples 100 --dry-run

# legacy 并发提交，先关闭随机失败做性能对照
python3 Test/run_cluster_tests.py --queue fat_x86 --samples 100 --jobs 20 \
  --mode legacy --submit-concurrency 16 --chaos off \
  --workdir Test/runs/legacy_100

# sidecar 小规模验证
python3 Test/run_cluster_tests.py --queue fat_x86 --samples 100 --jobs 20 \
  --mode sidecar --sidecar-path "$PWD/rust/target/release/donau-sidecar" \
  --submit-concurrency 16 --chaos off --workdir Test/runs/sidecar_100
```

默认保持原压力：奇/偶样本申请 2048/4096MB，实际分配 1.5/3GiB，100MiB IO，500 阶矩阵部分运算，runtime 60 分钟，10% 随机失败且规则重试两次。`--jobs` 控制同时在途作业上限。若只先验证调度链路，可显式加 `--stress-scale 0.001`；这会缩小分配/IO/CPU，不缩小申请的资源，不应当作原压力验收。`--runtime-minutes`、`--poll-seconds`、`--latency-wait` 也可以调整。

`--chaos random` 保持 10% 随机失败；`--chaos once` 使每十个样本之一首轮失败、后续成功，便于复现重试；`--chaos off` 用于性能对照。规则级重试可能在远端 Snakemake 内部完成，因此应同时检查作业日志中的失败和最终输出，不能只数调度器 FAILED 行。

样本 N 会产生 N 个压力作业和 1 个汇总作业，all 在本地执行。报告使用实际 dsub 调用/观察到的 ID 数量，不把 N 当作精确提交总数。

## 2. 1000 样本对照矩阵

三个后端使用独立目录和同一组参数；某组失败时停止矩阵，保留现场后再处理。serial 是 legacy 串行（并发=1），legacy 和 sidecar 使用 `--submit-concurrency`（默认16）。

```sh
python3 Test/run_cluster_tests.py --queue fat_x86 --samples 1000 --jobs 100 \
  --matrix --submit-concurrency 16 --chaos off \
  --sidecar-path "$PWD/rust/target/release/donau-sidecar" \
  --monitor-seconds 60 --require-state-sample 500 \
  --workdir Test/runs/matrix_1000
```

集群允许后再把 `--samples` 改成 10000，并选择新的 workdir。建议先观察100样本的调度器响应、内存和失败情况后放大。

默认使用很薄的 Python CLI 包装记录每次真实 `dsub/djob/dkill` 的耗时与参数，保持参数列表与输出流。其 Python 启动与追加日志会引入额外开销；各对照组保持一致，并可再用 `--no-cli-metrics` 跑一个不带包装的对照。这时仍有 Snakemake 总耗时、资源采样和独立真值采样，但没有 CLI 延迟分布。

`--poll-seconds` 是 Snakemake 检查间隔；sidecar 自身默认每5秒批量轮询，二者不同。资源采样每秒一次。`--monitor-seconds` 为额外的独立 Donau 真值采样间隔（默认60秒），完成后还会补一次终态采样；这些查询单独记录，不混入执行器 djob 调用统计。设为0可关闭真值采样，但无法启用 `--require-state-sample` 验收门槛。

## 3. 崩溃恢复与 legacy 回滚

先用较少作业和显式 hold 保证作业仍在运行。此命令只杀死它启动的 Snakemake 主进程，保留集群作业、日志和 journal；返回码3表示按计划完成故障注入。

```sh
python3 Test/run_cluster_tests.py --queue fat_x86 --samples 10 --jobs 2 \
  --mode sidecar --sidecar-path "$PWD/rust/target/release/donau-sidecar" \
  --hold-seconds 30 --chaos off --crash-after-submissions 2 \
  --workdir Test/runs/recovery_test
```

主进程停止后，用同一目录恢复。脚本复用原配置与 journal，等待旧代理释放 journal，再按显式 `--unlock` 清理 Snakemake 旧锁。

```sh
python3 Test/run_cluster_tests.py --resume Test/runs/recovery_test --unlock --mode sidecar
```

单独再建一个恢复用例、同样故障注入后，可用 legacy 恢复测试回滚路径：

```sh
python3 Test/run_cluster_tests.py --resume Test/runs/recovery_rollback --unlock --mode legacy
```

核对前后 control 目录的 summary/CLI 记录：旧作业应复用同一 Donau ID，sidecar 恢复日志出现 `[recover]`；legacy 回滚可结合 journal 与 CLI 记录核对。不能为同一仍在运行的输出新增 dsub。全量测试还会提交后续未开始的样本，不能把总 dsub 数量增长本身视为重复。UNKNOWN/无唯一匹配时保留现场，先用 `djob -u "$USER" -o "jobId name state"` 对账，不删除 journal 绕过去重。

## 4. 结果位置与判定

每次调用生成独立 `control/<时间>_<随机标识>/`，恢复调用不会覆盖前一次证据：

- `run.json`：版本、主机、命令、队列、参数、时间窗口、主进程 PID、退出码、端到端 wall time。
- `snakemake.log`：完整主进程日志；`logs/donau_executor.log`、`logs/donau_sidecar.journal` 在工作目录根部。
- `cli.jsonl`：包装开启时的真实 CLI 记录，区分状态、历史、诊断、恢复查询。
- `resources.jsonl`：主进程和 sidecar 的 CPU 时间、RSS；不等同 py-spy 调用栈。
- `monitor.jsonl`：独立 djob 真值、查询返回码与无法查到的 ID。不会把缺失状态当成成功。
- `summary.json`：dsub P50/P90/P99/max、调用数、提交跨度、状态比对结果与未验证 ID。
- 矩阵根目录的 `comparison.json`：三组端到端耗时对照。

`submission_span_including_dag_wait_seconds` 包含 DAG/依赖阶段等待，不是纯提交服务时间；单次真实 dsub 耗时另列。`observed_status_round_max_calls` 是基于活跃/历史调用顺序的分组统计，恢复/失败/并行查询时须结合原始记录核对；不能把整个用例的 djob 总数当成一轮次数。

状态验证同时保留 executor 的终态报告和独立真值。`--require-state-sample 500` 要求至少500条终态报告完成比对、没有未验证报告；任何假成功/假失败都会使验收返回4。100样本灰度不满足500条阈值，不应因此宣称完整验收。若命令失败、历史延迟或UNKNOWN使证据不足，保留日志并对账。

退出码：0=工作流和已启用的验收门槛通过；1/其他非零=工作流/命令失败；2=测试配置错误；3=预期的主进程故障注入；4=状态验证不通过、证据不足或指定 sidecar 的用例发生降级。

重新汇总已有证据，不提交新任务：

```sh
python3 Test/run_cluster_tests.py --report-only Test/runs/sidecar_100
```

最终请保留整个测试 workdir（包括日志、journal、control 和结果），以及目标集群的 CLI 版本、节点数、测量时段背景负载。真实平台性能、CLI输出格式和文件系统 fsync/flock 行为以这批实测为准。

## 5. 补齐真实基线的调用栈与背景记录

在同一登录节点的另一终端，对正在运行的1000样本测试取3次调用栈。先从该 workdir 的 `latest-run.json` 找到 control 目录，再读取其 `run.json` 中的 `pid`（这是 Snakemake PID）。以下值替换为实际路径和 PID：

```sh
DONAU_TEST_PID=12345
DONAU_TEST_CONTROL=/path/to/workdir/control/实际目录
for DONAU_SAMPLE in 1 2 3; do
  date -u '+%Y-%m-%dT%H:%M:%SZ' > "$DONAU_TEST_CONTROL/pyspy_${DONAU_SAMPLE}.txt"
  py-spy dump --pid "$DONAU_TEST_PID" >> "$DONAU_TEST_CONTROL/pyspy_${DONAU_SAMPLE}.txt" 2>&1
  if [ "$DONAU_SAMPLE" -lt 3 ]; then sleep 60; fi
done

date -u > "$DONAU_TEST_CONTROL/background-time.txt"
djob -u "$USER" -o "jobId name state" > "$DONAU_TEST_CONTROL/background-djob.txt" 2>&1
```

若未安装 py-spy 或集群禁止 ptrace，保留失败输出，不能把资源时间序列当作调用栈采样。另记集群名称、队列可用节点数量、站点节点负载命令的输出和测量时段；这些站点信息无法仅靠插件推断。真实 I/O 等待占比需要结合主/子进程 CPU 与调用栈判断，不能用“主进程CPU低”直接宣称超过90%。
